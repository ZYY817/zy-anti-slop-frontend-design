# C7 · 无障碍合规与自动化测试

> C4 讲"无障碍原理"，B76 讲"ARIA 实操"，本文件讲**"如何合规 + 如何自动验证"**。
> 2025 年起无障碍从最佳实践变成法律义务（欧盟 EAA 2025.6.28 生效），不只是"做好事"而是"必须做"。

---

## 一、合规时代（为什么现在必须做）

- **欧盟《欧洲无障碍法案》(EAA)**：Directive 2019/882，**2025-06-28 起在全部 27 个成员国直接强制执行**
- 技术标准 = **EN 301 549 v3.2.1**（实际对齐 **WCAG 2.1/2.2 Level AA**）
- 覆盖范围（B2C 服务）：电商网站/App、银行、电信、流媒体、交通购票、电子书
- 豁免：微型企业（<10 员工 且 年营收/资产 <€200 万，仅限服务部分）；归档内容（2025 后不更新）
- 过渡期：2025-06-28 前已存在的服务 → **2030-06-28 前合规**；但新服务从 2025-06-28 起**必须立即合规**；重大变更重置时钟；2030 不是安全港——投诉现在就能提交，监管已开始行动
- 现实压力：欧洲大型采购商 RFP 已把"有文档化合规声明"作为准入门槛；不合规名单被公开索引，影响品牌
- 商业价值（不是纯成本）：SEO 提升（语义 HTML/alt/标题层级）、**转化提升 10-20%**、全球 ~15% 人口有残障（临时/情境性残障更多）

### 常见失败模式（审计重点）

- 低对比度、缺 alt、图片文字、视频无字幕/音频描述
- 键盘陷阱、无焦点指示、触控目标 <24px
- 自定义组件（日期选择器/combobox/toast）缺 ARIA 模式（WCAG 4.1.2）
- 动态内容变化不播报（WCAG 4.1.3）

### 合规路线图（12 步浓缩）

```
Phase 1 范围界定（第1周）：列全部面向 EU 的表面（含结账/后台/帮助文档）；确认标准=WCAG 2.2 AA via EN 301 549
Phase 2 审计（2-6周）：axe/Lighthouse/WAVE/Pa11y 自动化基线（只抓 30-40% 问题）→ 专家评审 → 屏幕阅读器实测 → 优先级修复清单
Phase 3 修复+证据：逐条映射 success criterion → 修复 → 生成合规文档（供法律/RFP 用）
Phase 4 持续：CI 集成自动扫描、季度复测、新功能上线前验收
```

> ⚠️ **自动化扫描只能抓 30-40% 的 WCAG 问题**（机器可查的对比度/alt/ARIA 语法）。
> 剩余 60-70%（键盘体验、读序、语义判断）必须人工 + 屏幕阅读器验证。

## 二、AI 生成界面的无障碍默认规则

在 prompt / CLAUDE.md 中固定以下约束（写进设计系统，见 B82 同款思路）：

```
<accessibility>
- 语义化 HTML：真实 <button>/<a>/<form>/<label>，不用 div 冒充
- 所有图标有 aria-label 或 aria-hidden="true"（装饰性）
- 颜色不是唯一状态信号（error 除了变红还要有文字/图标）
- 表单错误要 announce（aria-live / role="alert"）
- Dialog：焦点 trap + 关闭后焦点归还 + Esc 关闭（见 B76）
- 键盘全可达：Tab 顺序、:focus-visible、无键盘陷阱
- 触控目标 ≥ 44px（或按平台规范 24-48px）
- 尊重 prefers-reduced-motion：动效降级
- 对比度满足 WCAG AA：正文 4.5:1，大字号/UI 组件 3:1
- 图片/媒体提供 alt 或 role="presentation"
</accessibility>
```

## 三、自动化测试工具链（把无障碍变成 CI 关卡）

| 阶段 | 工具 | 查什么 |
|---|---|---|
| 编辑器内 | axe DevTools、Lighthouse 无障碍分 | 实时标记缺失 ARIA/对比度/键盘缺口 |
| 构建时 | axe-core + jest/playwright 断言 | 关键流程回归 |
| CI/CD | pa11y、Lighthouse CI、axe 扫描 | 每个 PR 必跑，失败即拦 |
| 视觉回归 | 对比度计算、色觉模拟（Sim Daltonism） | 颜色唯一信号、低视力渲染 |
| 人工兜底 | 屏幕阅读器（NVDA/VoiceOver）走查 | 真实语义体验 |

## 四、无障碍验收四步（任何 AI 产交付前）

```
1. 键盘全走一遍  —— Tab/Enter/Esc/方向键 无陷阱、焦点可见
2. 屏幕阅读器过一遍 —— 读序合理、标签完整、错误有播报
3. 对比度批量测  —— 所有文本/UI 组件对背景 ≥ 阈值
4. reduced-motion 检查 —— 关闭动效后信息不丢失
```

## 五、生成代码的 Runtime Review（不只是"看起来对"）

QubitTool 2026 前线审查纪律：**"看起来对"不是测试规格。**

审查清单：
- [ ] Dialog 焦点 trap + 归还正确
- [ ] 表单错误有文本 + 被 announcement
- [ ] 图标有可访问名称
- [ ] 颜色不是唯一状态信号
- [ ] 触控目标 ≥ 44px（移动）
- [ ] 尊重 prefers-reduced-motion
- [ ] 对比度达标
- [ ] 语义标签正确（非 div 冒充按钮）
- [ ] untrusted HTML 处理、URL 处理安全

## 六、常见"AI 默认就错"的点（重点盯）

| AI 默认 | 正确 |
|---|---|
| 用 div+onClick 做按钮 | 真 <button>，含键盘/焦点/语义 |
| 图标无 label | 功能性图标 aria-label，装饰性 aria-hidden |
| error 只变红 | 文字 + 图标 + announce |
| Modal 不做焦点管理 | focus trap + 归还 + Esc |
| 动效无 reduced-motion | 提供降级 |
| alt 写 "image" 或留空 | 有意义描述或 role="presentation" |
