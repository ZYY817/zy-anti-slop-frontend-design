# Z3 · 前端质量审计与迭代闭环

> **定位**：生成结束不是任务结束。Z3 把“看起来不错”变成可观察、可评分、可修复的质量协议。

---

## 一、交给 Coding Agent 的审计指令

```markdown
你已经生成了一个前端页面。不要直接宣布完成。

先运行五轮审计，并把每个问题分为 P0/P1/P2/P3：

1. 视觉与品牌：层级、构图、节奏、比例、字体、色彩、材质、焦点、原创性。
2. UX 与内容：核心任务、信息架构、真实文案、CTA、数据、空/错/加载状态。
3. 交互与响应式：键盘、反馈、触控、移动端重排、长短内容、断点和状态流。
4. 工程与可访问性：语义 HTML、ARIA、focus、对比度、性能、CLS、组件复用、控制台错误。
5. AI 味与完成度：模板化痕迹、无意义装饰、重复卡片、默认紫色渐变、假数据、半成品状态。

对 P0/P1 问题立即修改实现，再重新检查；不要只给建议。
最后输出修改前后对照、未解决风险、评分和下一步。
```

---

## 二、五轮检查表

### Round 1 · Visual / Brand

- [ ] 3 秒内能看出页面是什么、为谁服务、最重要动作是什么
- [ ] 眯眼后有明确主焦点、次焦点和留白，不是同尺寸卡片平铺
- [ ] 字体层级、行宽、字重、基线和数字排版形成系统
- [ ] 色彩有角色和层级，不是随机彩色点缀
- [ ] 光、材质、阴影、圆角和图形语言一致
- [ ] 每个装饰都服务内容、品牌或导航，不是填空
- [ ] 至少有一个可解释的产品签名，不靠 logo 才能识别

### Round 2 · UX / Content

- [ ] 每个 section 只有一个主要职责
- [ ] 首屏标题和 CTA 具体，不是“解锁未来/提升效率”式空话
- [ ] 使用真实或合理模拟的数据结构，数量、单位、日期、状态彼此一致
- [ ] 空状态、加载状态、错误状态、成功状态、权限状态有内容和下一步
- [ ] 表单错误说明发生了什么、为什么、如何修复
- [ ] 信息密度与产品类型匹配，关键内容不被装饰淹没

### Round 3 · Interaction / Responsive

- [ ] hover、active、focus-visible、disabled、loading、success/error 逻辑完整
- [ ] 所有操作都有可见反馈，破坏性操作可撤销或明确确认
- [ ] 移动端是重新编排：导航、栅格、顺序、媒体和密度都重新决策
- [ ] 长标题、长用户名、0/1/10000 条数据不会破版
- [ ] 键盘、触控、屏幕阅读器路径都能完成核心任务
- [ ] reduced-motion 下仍保留状态和方向信息

### Round 4 · Engineering / A11y / Performance

- [ ] 语义标签、标题层级、label、alt、ARIA 与 DOM 顺序正确
- [ ] focus ring 可见，Dialog/Popover 有焦点管理和 Escape 行为
- [ ] 正文、链接、图标和状态通过对比度与非颜色线索可辨识
- [ ] 图片有尺寸、比例、现代格式和懒加载策略；LCP 媒体优先加载
- [ ] 不因字体、图片、数据或动画造成 CLS；动画优先 transform/opacity
- [ ] 组件有清晰边界，变体不靠重复 JSX 和类名地狱实现

### Round 5 · Genericness / Originality

- [ ] 没有无上下文的 AI 紫色渐变、Bento 堆叠、玻璃卡片、巨大 CTA
- [ ] 没有用“高级/现代/惊艳”替代具体设计决策
- [ ] 参考产品只借鉴规律，没有复制品牌表面
- [ ] 视觉强度有节奏，不是每一屏都在抢注意力
- [ ] 设计个性由内容、品牌、交互和媒介共同产生

## 三、评分模型

每项 0-5 分，低于 3 分必须有修复动作：

| 维度 | 权重 |
|---|---:|
| Product / UX | 18% |
| Visual / Brand | 18% |
| Content | 12% |
| Interaction / States | 12% |
| Responsive | 10% |
| Accessibility | 10% |
| Performance | 8% |
| Engineering | 6% |
| Originality | 6% |
| **总分** | **100%** |

总分不能掩盖单项崩溃：任何 P0 未修复，或 Accessibility / Product / Interaction 任一项低于 3 分，都不能标记为完成。

---

## 四、修复顺序

```text
P0：功能不可用、核心任务无法完成、严重无障碍/数据错误
→ P1：信息层级、状态缺失、移动端破版、明显模板感
→ P2：视觉精度、动效、内容润色、性能细节
→ P3：实验性 delight、微妙装饰、非核心优化
```

每轮修复都记录：

```text
Issue → Evidence → Decision → Change → Re-check → Result
```

## 六、压测模式

配合 [T1-前端能力压测基准.md](T1-前端能力压测基准.md) 使用时，Z3 不只审计单次结果，还要比较：

```text
V0 Native → V1 Knowledge → V2 Iterated
```

必须分别记录：

- 知识库带来的改善；
- Z3 修复带来的改善；
- 没有改善或产生副作用的 Prompt；
- AI 味仍然存在的具体证据；
- 应该升级已有哪个文件，而不是泛泛写“继续加强视觉”。

---

## 七、蓝图审计

在检查代码之前，先检查设计蓝图是否成立：

- [ ] 页面区域有职责，不是组件名称堆叠
- [ ] 内容层级和视觉层级一致
- [ ] Typography Contract 能承受长标题、短标题和多语言
- [ ] 布局模式与产品任务、内容密度相符
- [ ] 背景/媒体有角色、焦点、安全区和降级方案
- [ ] UI 组件有选择理由和“何时不用”
- [ ] Desktop / Tablet / Mobile 是重组关系，不是单纯缩放
- [ ] 视觉效果没有代替产品逻辑

如果蓝图失败，先修蓝图再修 CSS；不要用阴影、渐变、动画或装饰掩盖结构问题。
