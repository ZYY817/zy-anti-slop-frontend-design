# M3 · DesignOps 设计运营与评审流程

> 本库其他文件都是"设计知识"，本文件是"**如何运作设计工作**"。
> 解决：评审没有章法、反馈没有方向、handoff 丢细节、治理失控。
> 即使单人/AI 工作流，也需要"评审仪式"来保证质量闭环。

---

## 一、设计评审仪式（Critique）

### 评审要什么（先声明，再展示）
> Dropbox 的"蓝盒子法"：评审前在文档顶部列出——**我们想要什么反馈 / 不想要什么反馈 / 谁是最终决策者**。

示例蓝盒子：
```
本次评审想要的反馈：
- 视觉层级是否清晰（不想要：配色偏好）
- 空态与错误态是否完整（不想要：动效时长建议）
最终决策人：产品负责人
```

### 有效反馈框架（避免"我不喜欢"）
| 坏反馈 | 好反馈 |
|---|---|
| 这个颜色不好看 | 主按钮对比度不足，CTA 层次和次级按钮拉不开 |
| 这里怪怪的 | 标题跳号从 H1 直接到 H3，中间层级缺失 |
| 太挤了 | 卡片内间距 24px 密度高于导航 16px，密度体系不自洽 |

### 评审节奏
- 小改动：结对即时评审
- 迭代稿：周会 critique（限定 20-30 分钟，一次只评一个维度）
- 大版本：走查 + 多学科评审（设计/工程/内容/无障碍）

## 二、DesignOps 四轨模型（2026）

| 轨 | 内容 |
|---|---|
| Workflows | 从 brief → 设计 → 评审 → handoff 的端到端流程，模板化、设关卡（decision gates） |
| Adoption | 设计系统使用率、贡献规则、新团队 onboarding |
| Tooling | 工具链集成：Figma ↔ tokens ↔ 代码仓库 ↔ 文档 |
| Measurement | KPI：设计系统 adoption 率、time-to-handoff、评审周转、缺陷率 |

### 八阶段组件生命周期（成熟系统）
需求 → 探索 → 提案 → 评审 → 实现 → 发布 → 推广 → 维护/退役

### 成熟度四阶
1. 临时（每人各搞各的）→ 2. 沉淀（有 tokens/组件）→ 3. 治理（有所有权+评审）→ 4. 规模化（跨团队跨平台）

## 三、设计师 ↔ 开发者 Handoff

### 导致 handoff 摩擦的信号
- 多份组件库版本并存
- 开发者收到不完整 spec，重复实现已解决的问题
- 评审没人有最终决定权，流程卡住
- 新人 onboarding 靠口口相传

### 干净的 handoff 要素
- **spec 完整**：尺寸/间距/字号/状态/响应式规则齐全（见 D5-界面结构蓝图）
- **tokens 先行**：颜色/字体/间距走 token，不写死数值（见 D3）
- **状态与异常明确**：hover/active/loading/empty/error 五态图
- **语义优先**：先给语义 HTML 结构，再谈视觉（无头部分类规范）
- **可验证**：交付后跑视觉回归 + 无障碍审计（见 T2/C7）

## 四、治理（Governance）

| 项目 | 规范 |
|---|---|
| 所有权 | 每个组件/令牌有明确 owner |
| 贡献规则 | 新组件的准入标准（含无障碍验收） |
| 版本化 | v1.0/v1.1 更新日志，明确破坏性变更 |
| 审计节奏 | 季度组件去重、token 覆盖率检查 |
| 设计-代码同步 | Figma 库 ↔ 代码仓库 parity 维护 |
| 命名规范 | 统一的命名约定，避免同物多名 |

## 五、AI 工作流下的 DesignOps（单人也可用）

即使只有一个人 + AI，把"人"换成本文件原则：
- **决策门**：生成前先写 brief（约束/非目标/角色/状态/验收测试，见 M1）
- **评审关卡**：AI 产出一律先过 Z3 五轮审计再交付
- **回写闭环**：同一问题反复出现 → 回写专题/控制层（见 M2/Z2）
- **版本纪律**：每个设计决策记录 decision log（假设/权衡/未决问题）

## 六、2026 实测数据与起步路径

### 治理 → 回报（有数据）
- **79% 的成熟设计系统有正式治理**，ROI 高出最多 **60%**（一致性=意图与现实的偏差更小）
- 治理不是"模式警察"：文档要有"怎么用/怎么贡献/找谁支持"，且定期更新

### 治理仪式普及率（zeroheight 2026 Design Systems Report）

| 仪式 | 有该仪式的团队 |
|---|---|
| Release notes（发布说明） | 56% |
| Roadmap（路线图） | 48% |
| Office hours（答疑时间） | 33% |
| Communication plan | 24% |

> 角色变化：DesignOps 从业者 5%→8%，工程背景 12%→20%——设计系统正从"设计部门的事"变成跨职能基础设施。

### 常用 KPI 集（选 3-5 个跟踪即可）
- 设计周期时间（time-to-concept / 概念审批迭代次数）
- 评审流程时长、handoff 时长、UI 打磨时间
- 交付频率、缺陷率、设计系统 adoption 率
- 干系人满意度、可用性测试结果、OKR 进展

### 最小起步路径（单人/AI 团队也适用）
```
1. 访谈+映射：列出当前工作流 5 大阻碍（找慢在哪/哪卡住）
2. 只选 1-2 个优先级（评审仪式 / onboarding / 单一真相源）
3. 定义 1 个共享评审仪式（蓝盒子 + 20-30 分钟节奏）
4. 建立 1 个"活跃设计文件"单一真相源
5. 每周留时间复盘流程 → 季度迭代 playbook
```
> 没有 owner 的运营 = 人人重视但没人修。起步不需要专职岗位，设计负责人兼管即可；
> 团队规模参考：1 初级 : 2-3 资深；Retro 常被低估但价值最高。

## 检查清单（用于搭流程）

- [ ] 评审有明确 agenda + 想要的反馈类型（蓝盒子）
- [ ] 反馈落到具体原则/参数，不落"我喜欢/不喜欢"
- [ ] 每轮迭代有评审关卡（go/no-go）
- [ ] handoff 带完整 spec + tokens + 五态
- [ ] 每个组件/令牌有 owner + 版本
- [ ] 有季度一致性审计（token 覆盖率、去重）
- [ ] AI 生成物必过 Z3 审计 + T2 打分
- [ ] 反馈回路：教训回写知识库
