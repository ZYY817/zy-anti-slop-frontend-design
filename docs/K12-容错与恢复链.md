# K12 · 容错与恢复链

> 覆盖 5 个决策对象：撤销与破坏性操作、自动保存与多端冲突、离线与会话超时、异步请求反馈链（重试/竞态/防重）、死控件与空路径处置。

## K·撤销与破坏性操作（Undo / Destructive Actions）

- **领域**：容错/交互 · **成本**：低
- **定义**：高风险动作的可逆性设计——用撤销窗口替代确认弹窗，还是用确认拦截，取决于"错操作的代价 vs 打断成本"。
- **症状**：删一行数据弹三次确认；不可撤销的删除没有任何预警；Toast 撤销条出现得太快消失、来不及点；批量删除只撤销了最后一条。
- **适用**：CRUD 产品、内容管理、消息/列表操作 ｜ **不适用**：真正不可逆操作（转账/发布/删除账号）——这些必须确认，不能靠撤销。
- **决策点**：
  ① **确认 vs 撤销选型**——可逆操作一律 Toast+Undo（不打断）；不可逆才用 Modal 确认 + 显式输入名称/二次确认（C5）
  ② **撤销窗口时长**——默认 5s，批量/高价值操作延长到 8-10s；hover toast 时暂停计时
  ③ **撤销粒度**——单条撤销还是批量整组撤销？删除 3 条是发 3 个 toast 还是 1 个"已删除 3 项"？（后者，队列治理见 K14）
  ④ **实现模式**——软删除标记 + 延迟真删（窗口内可恢复）vs 记录逆操作回放；软删除需定真删时机与审计可见性
- **实现**：
  - 软删除：记录 deleted_at，UI 即时移除 + toast `已删除 · 撤销`，窗口到点才真正 DELETE
  - 确认弹窗仅用于不可逆动作；确认文案说后果不说废话（"永久删除，不可恢复"）
  - 撤销后要恢复原位置/原选中态（衔接 K4·无效放下的"回位"语义）
- **验收**：可撤销操作无 Modal 打断；撤销窗口内有且仅有一条恢复入口；不可逆操作有显式二次确认且文案说明代价；批量操作撤销整组生效。
- **衔接**：C5:190-195（何时不该弹确认）、C3（启发式容错原则）、K14·Toast队列、B14（边界态）、B84（反操控）

## K·自动保存与多端冲突（Autosave / Edit Conflicts）

- **领域**：容错/数据 · **成本**：中
- **定义**：编辑内容按节奏自动持久化，及同一内容被多处编辑时的合并/提示策略。
- **症状**：写了一半刷新全丢；自动保存太频繁导致输入卡顿；"已保存"指示一直转让人不敢关；两台设备编辑后一版覆盖另一版无声丢失。
- **适用**：编辑器、表单长内容、资料页 ｜ **不适用**：单步交易表单（金额/密码——显式提交）、匿名轻内容。
- **决策点**：
  ① **保存节奏**——debounce 多久？库内现有取值不一（B51 30s / G5 1.5s / K3 1s）：文本编辑 1-2s debounce，结构化字段 blur 即存，大文档 30s 快照+退出前提示
  ② **保存指示**——"保存中/已保存/保存失败"三态放哪？编辑器顶部小字固定位；失败必须可见且给重试
  ③ **冲突处理**——乐观覆盖（后写胜）/ 版本检测提示合并 / 锁编辑？（协作产品用 OT/CRDT 超出本层，单人多端用"检测到冲突，保留哪个"提示）
  ④ **退出保护**——脏状态离开页面 `beforeunload` 或路由拦截提示
- **实现**：
  - debounce 保存 + 状态机：idle → dirty → saving → saved/error；error 态给"点击重试"
  - 冲突检测：保存时带 version/etag，409 响应提示"内容已在别处修改"给对比或强制覆盖选项
  - beforeunload 只在 dirty 且未保存时拦截（拦截即负体验，频次要低）
- **验收**：正常输入 2s 内出现已保存；刷新不丢内容；失败有可见提示+重试；双端同时编辑产生冲突提示而非静默覆盖。
- **衔接**：G5（编辑器规格）、K11·内联编辑、K12·异步请求链（重试）、B14、D4（saving 态）

## K·离线与会话超时（Offline / Session Timeout）

- **领域**：容错/系统 · **成本**：中
- **定义**：网络断开或登录态过期时，用户输入与操作的保全策略。
- **症状**：断网提交表单白屏丢全部输入；登录态过期后点了半天按钮全失败；离线时界面看起来正常但操作全是无效点击；恢复网络后要重新填一遍。
- **适用**：表单类产品、编辑器、移动端弱网场景、长会话后台 ｜ **不适用**：纯展示页、必须在线的实时协作。
- **决策点**：
  ① **离线感知**——`navigator.onLine` + online/offline 事件，断网时全局指示（顶部条）+ 交互降级（提交按钮 disable 或转队列）
  ② **离线排队**——断网期间的操作是否入队重连重放？（表单草稿必须本地保；写操作可入队，需防重放冲突）
  ③ **超时预警**——会话过期前 N 分钟预警弹层 + "保持登录"；过期后未提交内容先本地快照再跳登录
  ④ **恢复路径**——重连/重新登录后回到原上下文、恢复原输入（localStorage/sessionStorage 草稿）
- **实现**：
  - 草稿持久化：dirty 状态 debounce 写 storage（key 带表单/页面 id），登录/重连后检测草稿询问恢复
  - 超时预警：基于 token 过期时间提前 2-5min 弹层，"继续工作"续期
  - 离线指示：非侵入顶部条（不用 Modal），禁用写操作但保留浏览
- **验收**：断网时界面有明确指示且不丢已输入内容；超时前有预警；重新登录后回到原页面且草稿可恢复；离线操作重连后正确重放或明确失败。
- **衔接**：K12·自动保存（草稿共用 storage 路径）、K14（离线指示属最低打断级）、B14（边界态）、F4

## K·异步请求反馈链（Retry / Race / Dedup）

- **领域**：工程/交互 · **成本**：中
- **定义**：请求发出之后的完整反馈决策——失败重试、过期响应丢弃、重复触发合并。骨架屏/乐观更新已有深档（B73/B58），本词只管"请求飞了以后"。
- **症状**：快速切换 Tab 显示成上一个 Tab 的数据（竞态）；双击按钮提交了两单（防重）；失败后只有"重试"按钮没有自动恢复；列表筛选连续操作时结果错乱。
- **适用**：一切异步交互：筛选/搜索/分页/Tab 切换/提交 ｜ **不适用**：SSR 首屏（无交互态）、乐观更新已覆盖的本地先行场景（衔接 B58）。
- **决策点**：
  ① **重试策略**——手动重试（给按钮）还是自动重试+指数退避（1s→2s→4s，≤3 次）？网络类失败可自动，业务失败只手动；何时放弃并给降级态
  ② **过期响应判定**——序号比对（只渲染最新请求）/ AbortController 取消 / 响应到达时检查上下文是否仍有效？（推荐 Abort 或 requestId，G5 已示范）
  ③ **提交期防重**——按钮 loading 期间 disable（B51 已覆盖）不够：还需幂等 key 或请求合并（双击/刷新重复提交同动作 → 单请求）
  ④ **失败可见性**——错误落在哪？（表单内联 > toast；数据区失败就地给重试位，不空屏）
- **实现**：
  - AbortController：每次触发 abort 上一个 `controller.abort()` 再发新请求；fetch 传 `signal`
  - requestId 自增：`if (id !== latestId) return;` 防过期响应落地
  - 防重：提交按钮 disable + 后端幂等（Idempotency-Key）；列表操作类连续触发做 leading+trailing 合并
  - 自动重试只对 GET/幂等操作；POST 一律手动确认重试（防止重复扣费/重复提交）
- **验收**：快速切换上下文不显示过期数据；双击不产生两单；自动重试只发生在幂等请求且 ≤3 次后给降级；失败信息就地可见。
- **衔接**：G5:282（AbortController 示范）、B58:532-582（乐观更新与回滚）、B73（骨架/兜底重试）、B51:243（提交期禁用）、K16·搜索触发链、K7·状态机

## K·死控件与空路径处置（Dead Control / Empty-Path Disposition）

- **领域**：容错/诚信 · **成本**：低
- **定义**：界面上"看起来能用实际没接"的控件与路径的处置——示能撒谎是 AI 生成界面的高发残留（B9 false affordance 的工程版）。
- **症状**：复选框有 cursor/hover/勾选视觉却零 handler（cases/04·V0 实证，裁判两次点名）；`<a>` 无 href 的死导航链；`opacity:0` 隐藏但仍在吃点击的隐形按钮；演示期遗留的外露触发钮（"模拟新通知"按钮直接挂在产品界面上）。
- **适用**：一切界面，尤其生成物/mock/演示版（脚手架痕迹高发）｜ **不适用**：无。
- **决策点**：
  ① **处置三选**——接上（有真实路径）/ 诚实回执（disabled/置灰+说明为何不可用+给替代路径）/ 移除。**不允许第四态"放着"**：每个可示能元素必须三选一落地
  ② **诚实回执的形态**——disabled 控件给 reason（tooltip/"需要 xx 权限"/"即将上线"）；不做 silent disable（灰了但不知道为什么）
  ③ **演示痕迹隔离**——mock 的驱动器藏进代码（定时器/控制台函数/URL 参数 `?demo`），不暴露成界面按钮；用户视角的产品面上无"演示"字样
  ④ **审计方法**——挨个点：每个 cursor:pointer/hover 态/按钮样式元素必须产生反馈或状态变化；每个 `<a>` 必须有真实 href；`opacity:0`/`visibility` 隐藏元素检查是否仍吃事件（加 `pointer-events:none`）
- **实现**：
  - `pointer-events:none` 配合 `opacity:0` 隐藏，或改用 `visibility:hidden`（本身不吃事件）
  - 死链替换：无真实去向的导航项改 `button disabled`+reason，或整个区块移除
  - 回执文案说"为什么不行"+ "哪能行"（V1c 实证：disabled 控件附说明而非沉默置灰）
- **验收**：界面无零 handler 的可示能元素；无 `href="#"`/无 href 的 `<a>`；隐藏层不吃点击；无外露演示触发器；disabled 均带原因。
- **衔接**：B9（false affordance 定义）、K9·12（示能 vs 反馈辨析）、K10·维度4（示能检查）、K14·权限可见性、cases/04·judge-report-3
- **置信**：⚠️ 单任务三案例（V0 三处犯例 / V1c 一处正例）；处置三选规则待第二任务复验
