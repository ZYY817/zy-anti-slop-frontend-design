# K10 · 界面审计九维框架

> 升级已有界面时的审查脊柱：九个维度各配一句"核心问题"、该查什么、去哪个词条/文档。
> 与 Z3 的关系：Z3 是五轮通用审计流程（视觉/UX/内容/工程/原创性），K10 是"界面升级任务"专用的更细维度——**行为细节、空间衔接、动画中断**是 Z3 没有单独成轮的。建议作为 Z3 的界面升级分支使用，或独立快速扫描。

---

## 使用方式

```text
接到"升级这个界面"的任务
  → 按九维逐维问核心问题
  → 发现症状 → 命中 K 词条或 B/R/V 文档
  → 按词条决策点逐项给方案
  → 改完按词条验收字段自检
  → 第九维（真实验收）不达标 = 不算完成
```

**反模式**：九维不是用来"每维都改点什么"的清单——没症状的维度跳过，不为展示术语堆砌设计手法。

## 各维详解

### 维度 1｜视觉设计（静止时的品质与辨识度）

**扫描动作**：截屏 → 眯眼 → 遮 logo。
- 眯眼：层级是否还成立（B56/R1 测试法）
- 遮 logo：能否认出是谁家的产品（B85 原创性三问）
- 找共同分母：Inter/紫蓝渐变/三卡片/全 8px 圆角/居中 hero（B82 清单）
- 主色是否有"说法"（来源/气质映射，B10/B61/B70）
- **品质判定（非仅合规判定）**："没犯禁令"≠"好看"——抛开规则清单直问：这个界面放在真实产品里，第一眼像成品还是像作业？有无气质方向感还是只有"正确的默认"（cases/04 实证：合规但冷的产出会输给自由发挥的暖方向）

**典型症状→词条/文档**："没气质"→B77 艺术指导；"太像模板"→B82/R1·G7；"颜色脏"→B2/B64/R5。

### 维度 2｜信息设计（内容清晰与重点突出）

**扫描动作**：只读标题+CTA 能否复述页面目的（B25 批评语言法）。
- 每屏是否一个主信息（Hick's law/单一焦点，B56）
- 密度是否匹配用户任务（dashboard 密、landing 疏，B62 密度档）
- 内容真实度：无 lorem、有真实数据形态/状态文案（C6）
- 数据展示是否有工艺（tabular-nums、单位对齐、B29）

**典型症状→词条/文档**："找不到重点"→B56/B86；"挤成一团"→B62/B40；"内容假"→C6。

### 维度 3｜空间设计（距离、层级、边界的合理性）

**扫描动作**：拉参考线 + 放大看接缝。
- 间距是否 ∈ 尺度集合（4pt/8pt 或 token，B42/B72）
- 空间分组是否成立（组内近、组间远——亲密性，A2/B66）
- **接缝全扫**：双边框、圆角冲突、阴影断裂、色差发丝缝（K2 全套词条）
- 分隔手段是否过度（能留白就不用线，B66 六级）

**典型症状→词条/文档**："缝隙别扭"→K2·咬合；"元素对不齐"→K2·边缘连续性；"分割太重"→B66。

### 维度 4｜交互设计（操作与响应）

**扫描动作**：每个可操作元素问两个问题——"用户怎么知道能操作？操作后怎么知道成功了？"
- 示能线索：可点元素看起来像能点（B9 affordance/signifier）
- 反馈时序：<100ms 视觉反馈（不等数据，B45 三段式）
- 状态覆盖：默认/hover/active/focus/disabled/loading/empty/error 穷举（D4/B73）
- 键盘与焦点：Tab 顺序、focus-visible、焦点管理（B76/C4）

**典型症状→词条/文档**："点了没反应"→B45；"看着不能点"→B9；"焦点丢了"→B76。

### 维度 5｜动效设计（时间、曲线、节奏）

**扫描动作**：录屏慢放看曲线，不看效果看"时间感"。
- 时长：hover 150-200ms、按下 ≤100ms、展开 250-300ms、modal 300-400ms（B45 量化表）
- 曲线按目的选：进场 ease-out/退场 ease-in/物理感 spring（B5/B71/R12）
- 编排：入场三层/stagger/主从关系（B11/B71）
- 降级：prefers-reduced-motion 全关闭（B71/C4）

**典型症状→词条/文档**："动画生硬"→B5 缓动语义；"弹性滥用"→B71/R12；"无编排"→B11。

### 维度 6｜行为细节（K 板块主战场）

**扫描动作**：真的动手——拖、滑、悬停、快速连击、中途取消。
- 吸附类：阈值/拉动感/落位/失败（K1·吸附）
- 拖拽类：六态完整、碰撞检测稳定、无效放下有回滚（K4）
- 悬停类：意图判定、延迟不对称、触屏降级（K3）
- 滚动类：穿透/锁定/锚定/恢复（K6）
- 中断类：打断位置连续、速度接管、状态收敛（K5）

**典型症状→词条**："拖动卡"→K4·跟手；"松手不对"→K4·惯性+K5·速度接管；"划过菜单乱跳"→K3·悬停意图；"Modal 里滚页面"→K6·滚动穿透。

### 维度 7｜前端工程（实现质量）

**扫描动作**：DevTools 检查 + 读状态管理代码。
- 动画属性白名单（transform/opacity，R9/B45）
- 状态显式建模（K7·状态机，无矛盾态）
- 事件健壮性（Pointer 统一/capture/cancel，K7）
- Token 化（颜色/间距/圆角/动效参数出处统一，D3/B72）
- 还原度：实现=设计意图（T2 还原度）

**典型症状→词条/文档**："top/left 动画"→R9；"状态分裂"→K7·状态机；"魔法数字"→D3。

### 维度 8｜性能体验（流畅与鲁棒）

**扫描动作**：Performance 录屏 + 快速暴力操作。
- 帧率：动画/滚动 60fps，无长 Layout（K7·渲染管线）
- CWV：LCP/INP/CLS 阈值（F3 2026 标准）
- 暴力操作：连击/拖拽狂甩/快速切换——不崩不闪（K5）
- 长任务：>50ms 拆分；预加载策略合理（K8·预测性加载）

**典型症状→词条/文档**："滚动掉帧"→R9/K7；"点快了崩"→K5/K7；"导航慢"→K8·预测性加载。

### 维度 9｜真实验收（是否亲眼验证）

**扫描动作**：这是元维度——前八维的结论是否来自真机检查而非推测。
- 浏览器实开页面（不是读代码想象）
- 状态逐一见过：hover/active/focus/disabled/loading/empty/error
- 尺寸扫过：320/375/768/1024/1440 + 125%/150% 缩放
- 操作过程录屏：动画慢放检查曲线/中断/落位
- **没有实际执行的检查不得标记通过**（Z3 原则）

**典型症状→词条/文档**："应该是好的"→不合格，回到对应维度实测。

## 附录：可粘贴执行 Prompt（K10 工作流的最后一公里）

K10 是流程，下面两个 prompt 把它变成可直接发给 AI 的指令。**先用诊断 prompt，拿到决策点清单后再用修复 prompt**——不要合成一步，诊断与修复分开是质量闸门。

### 诊断 Prompt（只诊断，不修改）

```text
你是我的界面审计员。对以下界面 [贴代码/截图/URL] 跑一遍九维扫描，**只诊断，不写任何修复代码**。

九维：视觉设计 / 信息设计 / 空间设计 / 交互设计 / 动效设计 / 行为细节 / 前端工程 / 性能体验 / 真实验收。

对每一维输出：
- 核心问题：这一维在问什么
- 发现的症状：必须指出具体证据（元素名/行号/像素值/观察到的行为），禁止"感觉不太好"式描述
- 命中条目：该症状对应哪个 K 词条（K·吸附/K·拖拽/K·流式滚动...）或 B/R 文档
- 待答决策点：这个词条要求决定但当前实现没有答案的点
- 严重度：P0 阻断使用 / P1 明显质量 / P2 细节 / P3 锦上添花

规则（cases/03 实测回填）：
- 命中的是 B/R 指针文档而非 K 词条时：它没有"决策点"字段——把该文档的核心规范**转写为决策句式**列出（如 B82 → "字体选型方向？"）
- 症状存在但全库无对应条目时：不硬凑，标"库缺口"并在文末单列反哺清单（这正是新词条的来源）
- P0 判罚细则：主路径功能缺口（如"排到末位不可达"）或某用户群全灭（键盘/触屏/读屏）=P0；体验降级但有替代路径=P1
- 同一证据跨维归属：允许每维各记一次+互相引用；汇总表"症状数"按维内独立症状计

最后给一张汇总表：维度 | 症状数 | 最严重级别 | 命中词条。
没有症状的维度直接写"通过"并给一句证据，不要硬找问题。证据分级：代码审查可定 ✅；需浏览器/真机复核 ⬜。
```

### 修复 Prompt（先答决策点，再写代码）

```text
基于上一步的诊断结果修复。规则：

1. **每个命中条目先答决策点**——K 词条逐项写成 Decision/Reason/Spec 三行；→B/R 指针项没有决策点字段，按其核心规范给简答。词条给参数域时具体取值你来定并写明理由；库缺口条目（诊断标了"库缺口"的）按最相近词条自答决策点并标"自答"。任何决策点没有答案，不许写对应代码。
2. 每个修复保留现有业务功能、数据逻辑、可访问性与技术约束；"保留功能"指业务行为，不要求保留缺陷行为本身；不借机做无关重构。
3. 改完按词条的"验收标准"逐项自检：能核对的说证据（代码行/参数值），不能核对的标注"未验证"。
4. 按 P0→P1→P2 顺序修；每修一项报告：问题 → 改动 → 验证结果。
5. 不要为展示词条而加效果——症状不存在的词条不适用，明确写"不适用"。

最终输出：修复清单表（问题|词条|决策点答案|改动|验证）+ 剩余风险 + 无法验证项清单。
```

### 与 Z3 的分工

- K10 prompt 对 = **升级已有界面**（从症状反查词条）
- Z3 = **新生成页面**的五轮审计
- 同一场景可串联：Z3 审计发现的行为细节问题 → 转 K10 诊断 prompt 定位词条 → 修复 prompt 落地
