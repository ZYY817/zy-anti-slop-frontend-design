# K14 · 通知、打断与浮层治理

> 覆盖 5 个决策对象：打断层级升级链、Toast 队列治理、徽标与未读、浮层堆叠、权限可见性。
> Toast 的"皮"已有深档（D4 变体/V13 动效/C5 文案/R20 队列规则），但打断体系——什么级别走什么通道、队列怎么管、浮层谁压谁——散见 5+ 篇未聚合。本文件立决策对象。

## K·打断层级升级链（Interruption Hierarchy）

- **领域**：通知/交互 · **成本**：低
- **定义**：信息按重要程度选择打断强度——就地提示（零打断）→ toast（轻打断）→ banner（持续提醒）→ modal（强制处理）。同一件事不该升级过度，也不该弱到看不见。
- **症状**：一个无关紧要的"已复制"弹了 Modal；关键错误只出现在角落 toast 3 秒消失用户没看到；表单字段错误不用 inline 提示却弹 toast 让用户自己找字段。
- **适用**：一切有反馈信息的产品 ｜ **不适用**：无——这是基线决策。
- **决策点**：
  ① **通道分级**——inline（字段级错误/就地说明）< toast（操作成功的轻确认/可忽略信息）< banner（影响当前会话的持续状态：离线/降级/新版本中）< modal（必须决策/不可逆后果/阻断任务）
  ② **升级规则**——用户忽略 toast 的同类问题再次出现要不要升级？（连续失败 → banner；三次忽略 → inline 提示）
  ③ **降级规则**——能 inline 的不 toast，能 toast 的不 modal；Modal 只给"必须回答才能继续"的事
  ④ **打断成本表**——modal 打断成本=任务流中断，每次使用都要能答出"为什么必须打断"
- **实现**：
  - 分级映射表进设计令牌：`info→toast / warning→banner / error-field→inline / blocking→modal`
  - 同一来源的重复消息不重复打断（衔接 K·Toast队列去重）
  - **回看链路**——toast 的点击目标要闭环：升到 toast 的通知/事件应可点按定位到来源（面板→条目定位+短暂高亮，cases/04 两臂各自实现但此前无词条），点了没地方去的 toast 不该是可点样式
- **验收**：每种反馈能说出所在层级与理由；没有 Modal 用于纯通知；阻断性错误不被降级成 toast 一闪而过；可点 toast 的落点存在且有定位反馈。
- **衔接**：C5（文案与确认）、K14·Toast队列、B14（边界态分级）、D4（alert/banner 变体）、Z3（审计项）

## K·Toast队列治理（Toast Queue & Dedup）

- **领域**：通知/交互 · **成本**：低
- **定义**：多条 toast 并发时的排队、去重、优先级与生命周期管理。
- **症状**：批量操作一次弹出 8 条 toast 叠满屏幕；error toast 被后来的 success 挤掉还没看清；hover 想点"撤销"时 toast 倒计时归零消失了；同一报错反复刷。
- **适用**：有 toast 通知的产品 ｜ **不适用**：无 toast 体系（banner/inline 为主的产品）。
- **决策点**：
  ① **同屏上限**——≤3 条，超出排队（R20 已有规格）；堆叠间距 12px
  ② **优先级与去重**——error 不被 success 挤掉；同类消息合并计数（"3 个文件已上传"而非 3 条）；重复消息 5s 窗口内合并为一条 +N
  ③ **自动消失规则**——success 3-5s；warning 5-8s；error 需手动关；带 Action（撤销/重试）的 toast 不自动消失或延长到 10s；hover/focus 暂停计时
  ④ **读屏分道**——aria-live=polite（常规）/ assertive（仅 error 与阻断）；不能全 assertive（轰炸读屏）
- **实现**：
  - 队列结构：`{id, level, msg, action, createdAt}`；渲染只取 top3，error 插队到队首
  - 合并 key：`type+msg` 相同且时间窗内 → 更新同一条计数
  - 暂停计时：pointerenter/focusin 清 timer，leave 恢复剩余时长（不清零重计）；**若有进度条须与计时同源**（rAF 或共享 deadline——CSS 动画与 JS 计时分离会在暂停时撒谎，cases/04 实证）
- **验收**：同屏 ≤3 条；error 不被挤掉；批量动作合并为单条计数；hover 暂停计时；带 Action 的 toast 给出可操作时间窗；aria-live 分级正确。
- **衔接**：R20:1103-1105（队列规格源头）、V13:180-196（进出场动效）、C5（toast 文案）、D4:231-256（toast 变体）、C4（aria-live）、K12·撤销（带 Action 的 toast）

## K·徽标与未读（Badge / Unread Indicator）

- **领域**：通知/视觉 · **成本**：低
- **定义**：数字徽标、红点、NEW 标的计数逻辑与清零时机。
- **症状**：徽标永远显示 99+ 失去意义；点进去看了一眼出来徽标还在；未读点与数字徽标同时上两套标准；通知中心清了角标不清。
- **适用**：消息/通知/待办类产品 ｜ **不适用**：无未读概念的静态内容。
- **决策点**：
  ① **计数上限**——99+ 封顶；精确数只在 ≤99 显示
  ② **清零时机**——进入列表即清 / 逐条标记已读 / 显式"全部已读"？（推荐：进入不自动清，滚动经过或标记后才清，避免"看了但没看"）
  ③ **红点 vs 数字**——数字=有确切未读数（消息/待办）；红点=只需"有新东西"（设置项/新功能）；NEW 标=功能上线营销，限时消退
  ④ **层级穿透**——父级徽标聚合子级未读？（导航树要聚合，但同级不重复计）
- **实现**：
  - 计数源唯一（unreadCount 由后端/store 计算），不从前端 DOM 数
  - 清零走显式动作（标记已读/已读全部）或查看时长阈值，不绑定"路由进入"
  - 未读态视觉：加粗/底色/点，三选一并全站统一（B41 规则已全）；cases/04 验证一种合并形态——**指示器即操作控件**（未读点本身=标已读按钮，省一列操作位，触屏无 hover 时亦常驻可用），可作三选一外的第四形态，置信 ⚠️ 单案例
- **验收**：计数与真实未读一致；清零时机可解释（不会"进了又退出来徽标还在"也不会"没看就清"）；红点/数字/NEW 三种用途不混用。
- **衔接**：B41:123-149（未读点/99+/NEW 规则深档）、K14·打断层级、C5、G6（通知中心）

## K·浮层堆叠治理（Overlay Stacking）

- **领域**：浮层/空间 · **成本**：中
- **定义**：多层浮层（Modal/Drawer/Popover/Tooltip）共存时的层级规则、焦点栈与嵌套许可。
- **症状**：Drawer 里开 Modal，Modal 底下的 Drawer 还能滚；两层遮罩颜色叠加变全黑；Esc 关了底层浮层而不是最上层；tooltip 被 modal 遮罩压住看不见。
- **适用**：复杂后台、IDE 类产品、多级操作流 ｜ **不适用**：单浮层简单页面。
- **决策点**：
  ① **层级表**——base(0) < sticky(10) < drawer(40) < modal(50) < toast(70) < tooltip(80) 类似分级写进 token；谁压谁有表可查（P2 已有 z-index 分层）
  ② **嵌套许可**——Drawer 里开 Popover/Tooltip 可以；Modal 套 Modal 禁止（C2 反模式）；Drawer 套 Drawer 同层替换而非叠加
  ③ **焦点栈**——每层浮层入栈，Esc/关闭只作用栈顶；归还焦点给上一层的触发元素（B76 焦点归还）
  ④ **背景锁滚**——多层浮层锁滚只锁一次，关闭最外层才释放（衔接 K6·滚动锁定）；遮罩浓度不叠加（透明叠加深化的坑）
- **实现**：
  - 浮层管理器统一渲染（Portal 集中挂载），栈结构管理 focus/scroll-lock/esc
  - 遮罩只渲染一层（最深浮层的遮罩），或每层遮罩 `rgba` 不叠加计算
  - 分栏/resize 与浮层关系：浮层内内容不受外层 split 约束
- **验收**：Esc 只关最上层；焦点归还给触发元素；多层遮罩不加深；Modal 不套 Modal；锁滚在最外层关闭后正确释放。
- **衔接**：K6·滚动锁定、B76:15-58（焦点陷阱/归还）、C2:223（模态套模态反模式）、P2（z-index 分层）、B59（视觉层深）、D1（Modal≠Drawer≠Sheet 辨析）

## K·权限可见性策略（Permission Gating）

- **领域**：权限/交互 · **成本**：低
- **定义**：用户无权限的功能如何呈现——隐藏 / 禁用+原因 / 锁定+升级引导 / 只读。四种策略选错要么让用户找不到功能，要么让用户点了才发现不能用。
- **症状**：管理员截图里有的按钮普通用户找不到（无解释）；禁用按钮没有原因提示用户以为坏了；只读页面所有输入框看起来都能编辑点进去才灰。
- **适用**：多角色产品、SaaS 分级、后台权限 ｜ **不适用**：单角色简单应用。
- **决策点**：
  ① **四策略选型**——hide（用户永远不该知道存在）/ disable+tooltip 原因（功能存在但当前不可用，教用户怎么获得）/ lock+badge（付费墙/升级引导，功能是卖点要看见）/ readonly（可看不可改）
  ② **预告存在性**——付费功能是藏还是露？（露：功能可见性是营销；藏：免费用户的减噪——按转化目标定）
  ③ **混排表达**——只读字段与可编辑字段同表单时，只读字段弱化（去边框/灰字/无 hover）而不是禁用态混淆
  ④ **权限被撤销**——使用中途权限失效：优雅降级提示而非界面崩坏（B14 边界态）
- **实现**：
  - disable+reason：`disabled` + `title`/`tooltip` "需要管理员权限"；禁用原因必须可发现，禁用不做静默
  - lock：`lock icon + "Pro"`，点击进升级路径而不是无响应
  - 服务端兜底：前端隐藏只是 UX，权限校验必须在 API 层（安全非视觉决策）
- **验收**：每种权限态能说出选型理由；禁用项有原因可达；锁定项有升级路径；只读与禁用视觉不混淆。
- **衔接**：B83:102（AI 权限门）、G2:62（锁图标）、D4:442（permission-denied 态）、B14:193-195（权限撤销）、C5（升级引导文案）
