## 目录结构

```
cases/
  README.md              ← 本文件（协议）
  NN-案例名/
    before.html          ← 有缺陷的基线（刻意保留典型问题）
    audit.md             ← K10 诊断 prompt 的实际产出（症状|命中词条|决策点待答）
    after.html           ← 修复 prompt 的实际产出（决策点逐项作答后的实现）
    record.md            ← 对照记录：症状→词条→决策点答案→改动→验证结果
```

## 案例规则

1. **before 必须是真实缺陷**——不是稻草人，是 AI 生成时真会犯的错（默认字体/模板卡片/无决策的交互）
2. **audit.md 只诊断不改**——按 K10 诊断 prompt 格式输出，每条症状必须指到具体元素/行
3. **after.html 的每处改动必须能回溯**——record.md 里写清：命中哪个 K 词条、该词条的决策点逐项答案是什么
4. **验证诚实**——能核对的写证据（参数值/代码行），不能核对的标"未验证"；不许写"感觉好了"
5. **词条反哺**——案例中发现 K 词条决策点缺失或错误的，回写对应词条（M2 闭环）
6. **证据分级**——代码审查能定的写 ✅；必须浏览器/真机才能定的写 ⬜ 并说明缺什么验证手段

## 反哺 Prompt（record 写完后的写回动作）

record.md 的"词条反哺"段不是感想栏——把每条反哺交给这个 prompt 落成可执行的词条补丁：

```text
基于本案例 record.md 的"词条反哺"清单，为每条产出一份词条补丁，格式：

【词条】K·XXX（所属文件 KN-xxx.md）
【字段】症状 / 决策点N / 实现 / 验收 / 衔接（只改实际涉及的字段）
【补丁】可直接粘进词条的文本（≤6 行，含本案例实证参数）
【证据】record.md 第 N 项 + before/after 行号
【置信】实测验证 ✅ / 逻辑推理 ⚠️ / 单点存疑 ❓（❓ 的只进词条"适用边界"作警示，不进决策点）

过滤规则（M2）：
- 本案例只验证了一次的写法 → 标 ⚠️，措辞用"本案采用 X，参数域待多案例佐证"
- 纯主观偏好（本案好看但换个项目未必）→ 拒绝入库，写明理由
- 词条已有更优写法 → 放弃补丁，只留"已验证"证据行
```
